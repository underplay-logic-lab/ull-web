## 次の一手（優先度順）

1. **§14.8 の compile 停止は解決（原因確定 + 実測済み、2026-09-20）。残るは採用判断。**
   原因は「端数バッチでバッチ次元が動く」ではなく、minimax_h3 の forward の
   データ依存分岐 `if bool(is_pad.any())`（`transformer.py:529`）。バッチ>1 では
   pad あり／なしの両方が1ラン中に出て、2つ目で DiT 丸ごと再コンパイル（≒8分）。
   `compile_dynamic=True` は tensor 次元にしか効かない。詳細 docs §14.8。
   - **対策は効いた**: `model.block_compile: true`（50ブロック個別コンパイル・
     cache 上限 auto 100）で **停止が消滅**（最遅 step 間隔 7秒）。warmup も
     476.9 → **112.5秒**。job `yukipas_v8` で実測。
   - **ただし compile の速度利得は eager 比 -4%**（3.60 → 3.45 s/it）。
     稼ぎは compile ではなく**バッチ化**で、1画像 0.863秒 ＝ GUI 現行
     （1.80秒/枚）の **2.09倍安い**。「4倍」には届かない。
   - 生YAMLで `block_compile` が効くよう worker に pass-through を入れて
     デプロイ済み（`_cloud_safe_model_block` が model ブロックを作り直すため
     それまで無言で捨てられていた）。**未コミット。**
   - **次の一手（安い順）**:
     1. **バッチ1 + block_compile** を1本測る（GUI 現行条件 + block_compile だけ）。
        当たれば全 minimax_h3 ジョブの prep が **365秒短縮（≈¥114/ジョブ）**。
        クロスブロック融合が減るぶん s/it が落ちないかの確認が必須。
     2. 実効バッチを GUI へ開放するなら m 係数を **0.42 → 0.31** へ再校正
        （同一データセットの二点 1.80@実効1 / 3.45@実効4 から算出）。
     3. さらに原価を削るなら pad を作らない方向（キャプション長でバッチを
        まとめる／固定長パディング）で flash を維持。ai-toolkit 改造が必要。

   「月額固定費は0円」「秒単位の適正価格」が実態と乖離（月額サブスクが実在し、
